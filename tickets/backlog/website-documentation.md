# Astro + Starlight Website & Documentation Implementation

## 1. Objective

Implement a public website and documentation portal for this project using **Astro + Starlight**.

The final site should have the following structure:

```text
https://example.com/
    Product / project landing page

https://example.com/docs/
    Documentation

https://example.com/docs/<page>/
    Individual documentation pages
```

The website should be:

- Static.
- Fast and lightweight.
- Responsive.
- Easy to maintain.
- Deployable for free using **GitHub Pages**.
- Generated automatically from the repository.
- Compatible with the Markdown documentation already generated by the project.
- Easy for coding agents to modify in the future.
- Printable at both individual-page and complete-documentation level.

The website does **not** need elaborate animations or a complex visual design. Prefer a clean, professional developer-product aesthetic and simplicity over unnecessary frontend complexity.

---

# 2. Core Technology

Use:

- **Astro**
- **Starlight**
- Markdown / MDX where appropriate
- GitHub Actions
- GitHub Pages
- Pagefind/Starlight's standard search functionality

Avoid introducing additional frontend frameworks unless there is a clear technical reason.

In particular, do not introduce React, Vue, Svelte, a backend, database, or server-side infrastructure merely for the website.

The target should remain a **fully static website**.

---

# 3. Existing Repository

Before implementing anything, inspect the repository.

Determine:

1. Where the existing generated Markdown documentation lives.
2. How that documentation is generated.
3. Whether documentation generation is already part of CI.
4. The logical ordering/hierarchy of the documentation.
5. Whether documentation files contain links, images, diagrams, code blocks, or other Markdown extensions.
6. Whether any generated documentation should be excluded from the public site.
7. Whether the repository already contains website-related infrastructure.

Do **not** unnecessarily move or duplicate the existing documentation source.

The existing Markdown documentation should remain the source of truth wherever practical.

Prefer adapting Starlight to the repository rather than restructuring the repository purely to accommodate Starlight.

---

# 4. Target Architecture

Conceptually, the repository should support:

```text
Repository
│
├── Application source code
│
├── Generated Markdown documentation
│
├── Astro/Starlight website
│
└── GitHub Actions
       │
       ├── Generate/update documentation if required
       ├── Build website
       ├── Build complete documentation PDF
       └── Deploy static output
```

The exact directory structure should be chosen after inspecting the existing repository.

Do not create unnecessary copies of generated Markdown files if Astro/Starlight can consume them directly or if a lightweight build-time synchronization step is sufficient.

# 7. Documentation

Use **Starlight** for the documentation section.

The documentation should provide:

- Sidebar navigation.
- Table of contents.
- Previous/next page navigation where appropriate.
- Syntax-highlighted code blocks.
- Copy-to-clipboard functionality for code.
- Responsive/mobile navigation.
- Dark/light mode.
- Documentation search.
- Heading anchor links.
- Proper metadata.
- Accessible markup.
- Good default SEO.

Preserve existing Markdown as much as possible.

# 9. Documentation Search

Enable Starlight's standard static documentation search.

The search solution must:

- Work on GitHub Pages.
- Require no backend.
- Require no paid external service.
- Index the generated documentation.
- Work after a normal static site deployment.

Prefer Starlight's standard Pagefind-based search implementation unless there is a strong reason not to.

Verify that search works in the production build, not only in development mode.

# 10. Individual Page Printing

Every documentation page must support printing.

Provide an obvious but unobtrusive action such as:

```text
Print this page
```

The action should invoke the browser's native print dialog.

For example:

```js
window.print();
```

The printed version must contain the **documentation content only**, not the complete website interface.

Create appropriate print CSS using:

```css
@media print {
    ...
}
```

When printing, hide elements such as:

- Main site navigation.
- Documentation sidebar.
- Search.
- Theme controls.
- Mobile navigation.
- Previous/next navigation.
- "Print this page" button.
- Interactive UI that makes no sense on paper.
- Unnecessary footer content.

Preserve:

- Page title.
- Documentation content.
- Headings.
- Images.
- Tables.
- Code examples.
- Links where useful.
- Callouts/notes.

Pay particular attention to page breaking.

Avoid splitting these elements unnecessarily across pages:

- Code blocks.
- Tables.
- Images.
- Callouts.
- Headings from the content immediately following them.

Use appropriate CSS such as:

```css
break-inside: avoid;
break-after: avoid;
```

where appropriate.

The result should work well with:

```text
Print
```

and:

```text
Print → Save as PDF
```

in modern browsers.

---

# 11. Complete Documentation PDF

In addition to printing individual pages, provide a way to download the **complete documentation as a single PDF**.

The intended user experience is:

```text
Documentation

[Search]   [Download PDF]
```

or another sensible placement.

The complete PDF should be generated automatically from the same Markdown documentation used by the website.

Do not manually maintain a separate PDF document.

The pipeline should conceptually be:

```text
Markdown
   │
   ├──> Astro/Starlight ──> Web documentation
   │
   └──> PDF generation ──> documentation.pdf
```

The complete PDF should preferably include:

- Project/documentation title.
- Version, if the project exposes a meaningful version.
- Generation date if appropriate.
- Table of contents.
- All public documentation pages in their logical order.
- Page numbers.
- Clickable internal links where practical.
- Clickable external links where practical.
- Proper heading hierarchy.
- Readable code blocks.
- Images and diagrams.
- Sensible page breaks.

Exclude website-specific UI.

The PDF should look like a document/manual rather than screenshots of web pages.

Choose an appropriate open-source build-time solution after inspecting the actual Markdown and project environment.

The solution must:

- Run non-interactively in CI.
- Require no paid service.
- Be reproducible.
- Work within GitHub Actions.
- Not require maintaining a second copy of the documentation.

Document the chosen PDF-generation approach.

---

# 12. PDF URL

Make the latest generated PDF available from the website at a predictable URL.

For example:

```text
/documentation.pdf
```

or:

```text
/downloads/documentation.pdf
```

Choose whichever fits the resulting site structure best.

Provide a **Download PDF** link somewhere appropriate within the documentation UI.

---

# 13. Documentation Versioning

Do not build a complex documentation-versioning system unless the existing project requires one.

For now, the website should represent the documentation corresponding to the current/default branch.

However, structure the implementation so that future release-specific PDFs could reasonably be generated, for example:

```text
/downloads/documentation-v1.0.pdf
/downloads/documentation-v1.1.pdf
/downloads/documentation-v2.0.pdf
/downloads/documentation-latest.pdf
```

Do not implement this unless it can be done simply or the existing project already has a release/version workflow.

---

# 14. GitHub Pages Deployment

Deploy the site using **GitHub Pages**.

Use GitHub Actions to:

1. Check out the repository.
2. Install dependencies.
3. Generate documentation if necessary.
4. Build the Astro/Starlight website.
5. Generate the complete documentation PDF.
6. Include the PDF in the final static site.
7. Deploy the resulting static site to GitHub Pages.

The build must be reproducible locally.

A developer should be able to run an equivalent local command such as:

```bash
npm install
npm run build
```

or:

```bash
npm ci
npm run build
```

and produce the complete site.

If PDF generation requires an additional command, expose it clearly, for example:

```bash
npm run build:pdf
```

Ideally provide a top-level command that performs everything required for production:

```bash
npm run build
```

or:

```bash
npm run build:site
```

with the exact behavior documented in the README.


# 16. CI Triggers

The website should rebuild automatically when relevant files change.

At minimum, deployment should happen when changes affecting the public site reach the deployment/default branch.

Changes to generated Markdown documentation must result in updated documentation being deployed.

Avoid unnecessary workflows that cause multiple deployments for the same change.

# 17. Markdown Compatibility

Before integrating the existing documentation, inspect it for:

- Relative links.
- Relative image paths.
- Code fences.
- Tables.
- HTML embedded in Markdown.
- Mermaid or other diagrams.
- Custom Markdown syntax.
- Generated anchors.
- Cross-document links.

Ensure these work correctly in Starlight.

Do not silently remove unsupported content.

If transformations are necessary, implement them at build/generation time rather than requiring humans to manually fix generated files after every generation.

---

# 18. Images and Assets

Ensure documentation images work both:

- On the website.
- In the generated complete PDF.

Do not rely on development-only filesystem paths.

Optimize images reasonably, but do not introduce a complicated image pipeline without a clear benefit.

# 19. SEO

- Page descriptions where available.
- Canonical URLs where appropriate.
- Sitemap.
- `robots.txt`.
- Open Graph metadata for the landing page.

# 20. Accessibility

Use Starlight's accessibility features and preserve semantic HTML.

The custom landing page and custom documentation components should support:

- Keyboard navigation.
- Visible focus states.
- Semantic headings.
- Accessible links/buttons.
- Appropriate image alt text.
- Sufficient contrast.
- Reduced-motion preferences if animations are introduced.

Do not sacrifice accessibility for visual effects.

---

# 21. Performance

Keep the site lightweight.

Prefer static HTML and CSS.

Avoid client-side JavaScript unless required for functionality such as:

- Search.
- Theme switching.
- Print action.
- Other genuinely interactive components.

Do not introduce a SPA architecture.

---

# 22. Styling

Use Starlight's default design system as the foundation for documentation.

Customize:

- Project name.
- Logo if available.
- Accent/brand styling.
- Typography if necessary.
- Landing page.
- Print styles.

Avoid heavily overriding Starlight unless necessary.

The goal is to minimize maintenance while still making the website feel like part of this project.

# 23. AI-Agent Maintainability

Assume future changes will frequently be performed by coding agents.

Favor:

- Conventional project structure.
- Small components.
- Clear filenames.
- Minimal dependencies.
- Standard Astro/Starlight patterns.
- Configuration in code.
- Automated generation.
- Deterministic builds.

Avoid:

- Clever abstractions.
- Excessive indirection.
- Custom frameworks.
- Complex build scripts where simple scripts would work.
- Manual post-build steps.

Add comments only where they explain non-obvious decisions.

---

# 24. Dependency Policy

Before adding a dependency, determine whether Astro, Starlight, Node, CSS, or GitHub Actions already provides the required functionality.

Avoid dependencies for trivial functionality.

Any additional dependency should have a clear purpose.

In particular, be conservative about dependencies introduced solely for:

- Styling.
- Icons.
- Printing.
- Navigation.
- Markdown manipulation.

PDF generation is an acceptable reason to introduce dedicated tooling.

---

# 25. Error Handling / Build Validation

The production build should fail when practical for serious documentation problems such as:

- Broken internal links.
- Missing required assets.
- Invalid configuration.
- PDF generation failure.

Do not allow CI to report success if the website deployed but the required documentation PDF failed to generate.

# 29. Guiding Principle

Keep the architecture simple:

```text
                 Existing repository
                         │
             ┌───────────┴───────────┐
             │                       │
      Application source       Markdown docs
                                     │
                         ┌───────────┴───────────┐
                         │                       │
                  Astro + Starlight          PDF build
                         │                       │
                         ▼                       ▼
                  Static website       documentation.pdf
                         │                       │
                         └───────────┬───────────┘
                                     │
                               GitHub Pages
                                     │
                         ┌───────────┴───────────┐
                         ▼                       ▼
                   example.com/         example.com/docs/
```

The existing Markdown documentation remains the primary documentation source.

Astro/Starlight is the web presentation layer.

The PDF pipeline is an alternative presentation layer over the same documentation.

GitHub Pages is the hosting layer.

Keep these concerns separate so any one of them can be changed later without rewriting the documentation itself.
